# Mobile (Expo)

Contentra mobile is an Expo Router entrypoint backed by the same `/api/v1` contract as web. It uses the API-selected authenticated membership and sends the selected workspace ID on workspace-scoped requests; the server still validates membership and permissions.

## Environment

`EXPO_PUBLIC_API_URL` is the only mobile runtime setting. It is an API origin, never a secret. Do not add `DATABASE_URL`, `SESSION_SECRET`, `ENCRYPTION_KEY`, Gemini keys, Paddle API/webhook keys, or OAuth client secrets to Expo settings.

## Development and testing

Install workspace dependencies, set a reachable API URL, and run `pnpm --filter @contentra/mobile start`. Use `android` or `ios` after Android/iOS tooling is installed. The app stores the workspace selection and the API session token in SecureStore (the React Native fetch stack has no cookie jar, so `apps/mobile/src/api.ts` captures the `contentra_session` cookie from Set-Cookie, replays it as a `cookie` header on every request, and clears it on `401`). SecureStore is the OS keychain/keystore, not plain AsyncStorage. Test real-device cookie behavior using HTTPS or compatible development cookie settings.

## Deep links and OAuth

The application scheme is `contentra`. OAuth is initiated by the API and provider credentials remain on the API. The app listens for an app-link return and refreshes its authenticated workspace state; it never parses a provider token. Configure providers with the API callback URL generated by the server. If the API is later configured to hand control back to the app, use a route under `contentra://` (for example `contentra://oauth-complete`) after the API has validated the provider callback. Do not register that client URL as the provider token-exchange callback.

Billing opens the backend-issued Paddle checkout URL in the system browser. On return, the app refreshes backend subscription state; opening Checkout is not treated as a completed payment.

## Push and updates

The API accepts encrypted, workspace/user-bound Android and iOS device registrations at `POST /api/v1/workspaces/:workspaceId/devices`; the client (`apps/mobile/src/push.ts`) asks permission only when the user enables push, registers/refreshes its Expo token, and revokes on disable or sign-out. `registerForPushNotifications(workspaceId, prompt)` verifies the physical device and permission, requires `EXPO_PUBLIC_PROJECT_ID`, then submits `{ token, platform }`; it is called automatically after workspace restore and from the Settings push toggle. Delivery runs through the queue worker and `sendPushToWorkspace`; with no `EXPO_ACCESS_TOKEN` on the API the server reports `not_configured` (a documented no-op) rather than a fake sent status.

For updates, use `expo-updates`/EAS Update only for JavaScript-compatible releases. Native changes must be marked store-required in the release platform metadata and distributed by the App Store or Google Play. Use `GET /api/v1/releases/latest` to show update notices and persist the last-seen/dismissed state in SecureStore.
